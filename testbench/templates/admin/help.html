Draft, live and closed

What each status means for participants, data integrity, and researcher workflows.

Status What it means & rules
Draft Participants see “This study is being prepared” and cannot start. You can edit questions, prototypes, modules, and settings without restriction. Use Preview to test the flow yourself.
Live Participants can enter at the study link (and passcode if required). Changing questions now can make answers hard to compare, so the editor warns you. Use when actively fielding your study.
Closed Nobody new can enter and people inside cannot resume. All responses, reports, and CSV exports stay intact. You can reopen the study anytime by setting the status back to Live.
Offline Administrative hold. Participants see “This study is not available”. Data and configuration are preserved while platform operators review reported concerns.

You can switch status at any time using the status badge dropdown in the header or on the Launch page.

Choosing a module

Pick by the research question you need answered.

  • Which of two designs is easier to use?

    Use an A/B test. Each person does the same tasks across two interactive prototypes. You get task speed, completion rate, perceived ease ratings, sign test p-values, order effect checks, and a plain automated verdict.

    A/B test

  • Who are your participants, and what is hard for them?

    Use a survey. Great for screener criteria, user demographics, rating scales, or post-task open feedback. Place it first so subsequent modules can branch or filter based on responses.

    Survey

  • Where do people click first on a screen?

    Use a first click test on a static page mockup or screenshot. You get interactive click heatmaps, percentage of clicks inside the target area, and median time to first click.

    First click

  • How do people categorize and conceptualize your content?

    Use a card sort with 15 to 40 cards. Closed if you already have fixed categories, open if participants create their own, or hybrid for both. You get co-occurrence matrices, category agreement ratios, and popular groupings.

    Card sort

  • Where would people navigate in a text-only hierarchy?

    Use a tree test on your menu structure without visual design. You get overall task success rates, directness percentage (navigating without backtracking), and weakest task identification.

    Tree test

Modules can be reordered by dragging them on the Build page.

Launch checklist

Every check on the Launch page validates specific criteria before fielding.

  • Done

    All required configuration files, assets, and validation criteria are verified. Contributes to launch readiness score.

    Done

  • Warning

    A recommended practice is missing (e.g. consent statement for timing tracking, manual grading needed on A/B tasks, or single-member team). Advisory only — does not prevent launching.

    Warning

  • Blocks launch

    A critical requirement is unfulfilled (e.g. passcode access enabled without setting one, missing prototype file, or YAML syntax error). Must be resolved before switching status to Live.

    Blocks launch

Checklist items are evaluated dynamically whenever you make changes in the Studio or on the Launch page.

Reading results

Every sentence in a report is produced by a fixed rule, not written by a model. The same numbers always give the same sentence.

Term What it means
Indicative A report is marked Indicative until enough people have finished. The number is set in the module’s decision rule for A/B tests, and is 8 for the other types. Below it, no report says a design won.
Intervals A range next to a number shows how far it could be from the truth. If the 95% confidence interval range crosses zero, the difference may be chance, and the report says so.
A/B verdict Each check (speed, success, ease) reads for, against or unsure, then the overall line follows the strongest pattern: all three for, a mix of for and against, all against, or not enough evidence on any check. It is never stronger than the least certain check.
Order effect Only stated as a fact, for example “Search and filters is faster in both orders.” It never claims that order did or did not drive the result — that is not something the numbers alone can show.
Drop-off A module is flagged when at least 2 people and at least 20% stopped at the same point. One person leaving is not flagged.
Card sort agreement A card has a clear home when at least 70% of people used the same category. Between 50% and 69% indicates moderate consensus; under 50% is “no clear home”.
First click The share of people who clicked inside the target area, and the median time to their first click. First-click success strongly correlates with final task completion.
Tree test Success across all tasks, success without backtracking (directness ratio), and the single weakest task by name and share.
Sign test Where a check is about direction (for example, which variant was faster for each person), a p-value from the exact two-sided test is shown alongside it.

Reports can be viewed online or downloaded as raw CSV datasets from the Results page.

Editing as YAML

For researchers and engineers who prefer version control and text files.

Every study is backed by plain text YAML files stored directly on disk:

  • project.yaml defines study title, status, brand colors, participant identification mode, and consent statements.
  • modules/<module_id>.yaml configures individual module parameters, question sets, prototypes, and decision rules.
  • prototypes/ contains standalone HTML, CSS, and JS assets used by A/B testing and interactive modules.

Every module editor in the Studio has an Advanced tab with the exact YAML file. You can edit via the form UI or directly in YAML. Every save validates the entire study schema; if a syntax error or broken reference exists, no changes are committed to disk and line-numbered errors are reported immediately.

Access, identity and privacy

How authentication, passcodes, and participant privacy are safeguarded.

  • Anonymous sessions

    Participants receive a randomized resume code (e.g. WXYZ-4567) to resume their session if disconnected. Zero personally identifiable information (PII) is captured or stored.

  • Passcodes

    Shared study gatekeeper configured on the Launch page. Stored using salted cryptographic hashes (PBKDF2/SHA256) so the raw secret is never stored in plaintext.

  • Participant codes & emails

    Pre-assigned identifiers validated against allowed patterns or domain whitelists. Responses remain strictly isolated within each study's private SQLite database.

All participant sessions and module responses are stored locally in isolated SQLite databases per study.
